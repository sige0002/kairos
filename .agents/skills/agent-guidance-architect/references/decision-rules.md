# どの指示をどこへ置くか

各項目が何を改善し、どの誤りを防ぐかで配置を決める。
行数を減らすためだけに必要な境界を削らず、過去の失敗をすべて常時規則にもしない。

| 情報 | 主な行き先 | 判断の要点 |
|---|---|---|
| 毎回必要な認可・機密・データ不変条件 | `AGENTS.md` | ユーザー由来の意図を保つ。機械強制があっても判断に必要な境界は短く残す |
| 一行程度の正準 build/test 入口 | `AGENTS.md` | リポジトリから発見しづらい入口や順序の落とし穴を優先 |
| API・データ形式・サービス詳細 | 既存の仕様書 | 再記述せず、必要になる作業を添えてリンク |
| 特定作業の制約・手順 | Skill | description で発動範囲を識別できるようにする |
| 特定モードだけの長い例・手順 | Skill の references | 全参照を必読にしない |
| 特定ディレクトリでのみ変わる規約 | そのディレクトリの指示 | ルートとの差分だけ。パッケージ数で機械的に増やさない |
| Claude だけの機能・設定 | `CLAUDE.md` など既存のアダプタ | 共通指示を複製しない |
| フォーマットの詳細 | 既存の linter / formatter / CI | 指示に同じ設定値を並べない。設定変更を勝手に追加しない |
| 汎用的な励まし・既知の実装手順 | 削除候補 | 削ると失われる固有判断がなければモデルの能力に任せる |

## 発動条件と手順の粒度

description は「何をするか・いつ使うか」を短く示す。
例: migration のスキルを、DB や query を触る全作業へ発動させない。
専門レビューは、専門的判断を要する作業かレビュー依頼へ絞る。

ユーザーが選んだ設計・スタック・範囲を先に扱う。特定例の配色、テスト形式、
役割数、ツール名、承認段階を全作業へ強制しない。反復する処理には具体的な
停止条件を持たせ、認可済みの作業を初回実装だけで返さない。

複数のモードがあるスキルは共有制約とモード選択を入口へ置く。
長い仕様は既存の正本を使い、短い自己完結したスキルに空の references を増やさない。

## 互換性と測定

既存の `AGENTS.md` 正本 / `CLAUDE.md` の `@AGENTS.md` ラッパー、および
`.agents/skills/` 実体 / `.claude/skills/` symlink を保つ。
探索パス、import、文書サイズ上限を変更する判断では、対象ツールとバージョンの
現行資料を確認する。設定値を実行時の値と同一視しない。

`@import` へ移しただけでは常時コンテキストは減らない。
`measure_context.py` で対象 cwd と読み込み経路をそろえて前後比較する。
行数・推定トークン数はコストの代理指標であり、成功率の証拠ではない。
効果の主張には [evidence-matrix.md](evidence-matrix.md) と実タスク評価を使う。

根拠となる整理方針:
[OpenAI: Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。
他モデルも読む共有指示では、この記事を口実に固有の安全条件や契約を削らない。
