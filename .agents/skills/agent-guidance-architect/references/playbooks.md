# ガイダンス導入・移行の選択肢

必要なケースだけを使う。次の例は工程の補助であり、commit・設定変更・
外部公開・全アプリ検査を自動で認可するものではない。

## 新規リポジトリ

関連するマニフェスト・CI・既存コードから、判断に効く境界と正準コマンドを抽出する。
AGENTS.md に共通指示を書き、CLAUDE.md に `@AGENTS.md` と Claude 固有差分を置く。
テンプレートを使う場合は、プレースホルダーと不要な例を残さない。

複数ステップの反復作業や固有契約に必要なスキルだけを追加する。
両ツールで共有する実体は `.agents/skills/<name>/`、Claude 側は対応する symlink。
既存ファイルを確認してから配置し、名前衝突を上書きしない。

構造・リンク・frontmatter と、今回必要なコマンドを確認する。
リンター、hook、permissions の導入は、その変更も依頼範囲にある場合に扱う。

## 既存リポジトリ

対象ファイルと既存変更を確認し、広い整理なら変更前後を保存して比較可能にする。
対象 repo 全体を監査する例:

```bash
python3 .agents/skills/agent-guidance-architect/scripts/build_report.py \
  --repo . --out /tmp/guidance-report.md
python3 .agents/skills/agent-guidance-architect/scripts/measure_context.py \
  --repo . --cwd <relevant-subdirectory>
```

別 worktree や外部 submodule などが探索範囲へ混じる場合、対象だけの一時コピーを
使うか、対象ファイルを受け取る個別 checker を使う。fixture と template の意図的な
不正例を本番指示として修正しない。

1. 対象の本文を読み、固有の不変条件・認可・禁止・ユーザーの意図を記録する。
2. [decision-rules.md](decision-rules.md) で重複・汎用記述・作業別詳細を整理する。
3. 仕様の詳細は既存正本へリンクし、必要な参照だけを読める入口にする。
4. 全差分、リンク、import/symlink、発動条件を確認し、適用範囲をそろえて再測定する。

認可済みの整理で判断できる編集は進める。ユーザーの意図が不明な重要規則の衝突は
確認するが、削除のたびに承認を要求しない。checker の誤検出には理由を付ける。
PASS を得るためだけに有効な規則を弱めたり、無関係な設定へ変更を広げたりしない。

## 正本の統一

- CLAUDE.md だけなら、両ツールに必要な指示を AGENTS.md へ移し、Claude 固有差分を残す。
- AGENTS.md だけなら、Claude 共有が依頼範囲にある場合にラッパーを足す。
- 両方あれば、共通部分を AGENTS.md へ統一する。重要な矛盾は現行のユーザー意図と
  コード・仕様で裁定し、根拠を記録する。

既存のラッパーや symlink を無理由に再作成しない。Windows など symlink の前提が
異なる環境では、対象のツール仕様と既存の同期方法を確認して選ぶ。

## モノレポ

ルートには共通制約だけを置く。作業文脈が実際に変わる境界に限って、ルートとの差分を
nested AGENTS.md と必要な Claude ラッパーへ置く。全パッケージへ機械生成しない。
主要な cwd ごとに測定して、無関係な指示の混入や読み込み上限による欠落を調べる。
上限や除外設定はツールの現行仕様を参照し、古い数値を固定しない。

## 研究・行動評価

構造検査と行数比較だけでは、モデルの作業品質向上を証明できない。
成功率などを評価する依頼では、現実的な同じタスクを旧版/新版で比較し、条件、
繰り返し数、時間・コスト、判定者、失敗例を記録する。fixture はコピーで使い、
実装者が自分の期待する出力へ採点を合わせない。日常の文書整理へ一律に追加しない。

## 機密が見つかった場合

修正後も公開済み履歴は残る。資格情報なら露出範囲とローテーションの要否を報告し、
履歴書換えや権限変更は認可された範囲で扱う。機密値をレポートや検索コマンドへ
再掲しない。Kairos のロボット名は no-confidential-names の既存ゲートに従う。
